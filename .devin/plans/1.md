# VLM evaluation plan — Linux / one RTX 4090

## Goal and rules

Evaluate the exact ChartVerse-2B, Amsi-fin-o1, and VFAi-X 3.5 9B artifacts through `vlm_benchmark.py`. Run **one model server and one benchmark request at a time**: use one explicit `--models` key, `--workers 1`, and `--repeats 1`. Stop the server and confirm VRAM is released before loading the next model. Keep endpoints on `127.0.0.1`; neither the shim nor the local route provides authentication.

Use validation for load tests and setting selection. Finish validation for all three models and freeze each model's checkpoint, precision, prompt, pixel cap, and output cap **before** touching the held-out test split. Then test the models individually. Do not replace a failed fine-tune with its generic Qwen base and label the result as that fine-tune.

## Verified host and repo state (2026-10-11)

- One RTX 4090: 24,564 MiB VRAM, CUDA compute capability 8.9, BF16 supported; GPU was idle when checked. CPU RAM is plentiful (about 670 GiB available); there is no swap.
- The container's local `/` overlay is 30 GiB, with **about 22 GiB free** after installing dependencies. `/root` and `/tmp` are local but ephemeral when the container is replaced.
- `/workspace` is persistent `fuse.geesefs` network/object storage. It reports an apparent 1 PB capacity that is **not** a meaningful local scratch limit. Files are shown as owned by `nobody`; `chmod`, ownership changes, executable bits, symlinks, locking, and POSIX append/rename behavior cannot be assumed to work. The attempted venv there failed.
- The working `/root/.venvs/trading` has Python 3.12, CUDA-enabled torch 2.8.0+cu128, Transformers 5.18.0, Accelerate 1.14.0, FastAPI 0.142.2, Uvicorn 0.54.0, and bitsandbytes 0.50.0. `pip check` passed. These packages are now in `requirements.txt`; rebuild this ephemeral venv on container replacement or bake dependencies into the image.
- `nvcc` is present; `llama-server` and `vllm` are not on `PATH`. Build/use native Linux CUDA rather than Vulkan or WSL2.
- Registry keys and loopback ports already exist: `chartverse-2b-hf` → 8081, `amsi-fin-o1-hf` → 8082, and `vfai-x-9b-hf` → 8083. Select keys explicitly; `--first-pass` excludes them. The HF shim supports `--device cuda`, `--dtype bf16`, `--load-4bit`, `--max-pixels`, and `--max-new-cap`.
- A no-shot validation packet is a 1600×1000 chart plus about 8,050 characters of OHLCV/context. The CLI estimates roughly 6,500 input tokens; this is **not** an exact Qwen/llama.cpp token count. Validation has 8 charts and test has 20.

## Storage layout and persistence gate

Use `/workspace/vlm_artifacts/<model>/` for immutable, versioned **plain model files** and checksums, and `/workspace/vlm_runs/<protocol>/` for completed result snapshots, outside the Git repo. Use `/root/vlm_work/models/<current-model>/` for the active model, `/root/vlm_work/runs/<protocol>/` for append-heavy `runs.jsonl`, raw replies, and reports, and `/root/.cache/huggingface` for HF cache/locks. Do not set `HF_HOME`, a pip cache, or a venv to `/workspace`; do not execute binaries or memory-map large models directly from GeeseFS for the first pass.

1. Before expensive downloads, verify a small plain-file write/read round trip to the intended `/workspace` artifact and result locations; if it fails, stop and resolve storage access rather than attempting `chmod`/`chown` as root. Check the provider's actual object-store quota separately from `df /workspace`.
2. Acquire a **pinned model revision** on local POSIX scratch, verify complete files and SHA-256 checksums, and copy only regular file bytes plus a revision/precision manifest to `/workspace`. On a new container, stage those files back onto local scratch and verify checksums before loading. Avoid preserving ownership/modes or copying HF cache symlinks and lock files (`rsync -a`, `cp -p`, and `chmod` are not appropriate here).
3. Hold only the current model's weights on the local overlay. Avoid a second full-size HF cache copy when downloading into a local snapshot directory; watch `df -h /` during acquisition and staging. Keep the CUDA `llama-server` executable/build on local POSIX storage when running; a pinned build can be persisted as ordinary artifact bytes and restaged after a restart.
4. With `--split val|test`, `--root /root/vlm_work/runs/baseline` points the runner's mutable results at local disk while the chart dataset still comes from `data/resistance_dataset`. Restore the latest **verified complete** snapshot from `/workspace/vlm_runs/baseline` before resuming so successful calls remain cached. After each completed chart or small batch, copy the closed result files as a new, versioned snapshot and verify the readback before considering it persisted; retain the previous snapshot if the copy is interrupted. Do not append `runs.jsonl` directly on GeeseFS or depend on an atomic rename there. Use the same restored root for the eventual report.
5. Store fallback precisions/checkpoints in separate result roots (`baseline`, `vfai-bf16`, etc.). The current `run_key` does not include revision, quantization, endpoint, or pixel cap, so changing those behind the same key otherwise produces misleading cache hits. Record the exact runtime settings alongside each persisted snapshot.

## First-pass order and resource gates

1. **Offline pipeline check:** run one `--mock oracle` validation chart into a *separate* local `mock` root. This checks dataset paths, output writes, and parsing without loading a model. It must not enter the three-model leaderboard.
2. **Amsi-fin-o1 BF16 — verified working (2026-10-11):** revision `25e81519` stored at `/workspace/data/models/amsi-fin-o1-25e81519` (8.3 GB, checksums verified). The HF shim and dependencies are already present. No `--trust-remote-code` was needed (native `qwen3_vl` support in Transformers 5.18.0). Run with `--device cuda --dtype bf16 --max-pixels 802816 --max-new-cap 8192` on port 8082. **Confirmed settings:** the 2048-token cap truncated it (Thinking fine-tune), and the registry's original `temperature: 0.0` forced greedy decoding and caused an infinite repetition loop; the registry entry now carries `temperature: 0.6, top_p: 0.95` (Qwen3-thinking recommended sampling), after which generation terminates normally. **Val split outcome (cap 8192):** 3 of 8 charts completed ok (PTON, RIVN, RKLB; F1@0.5 ATR 0.469 over those 3). 5 hit the length cap: RIOT and SNAP were genuinely truncated mid-reasoning (a larger cap should finish them); SNDL and SOUN are degenerate repetition loops and SOFI an endless enumeration, which a larger cap will not fix — they need `repetition_penalty`/`top_k` support (small shim change; currently only `temperature`/`top_p` are passed) or must be accepted as a model limitation. Retry attempts must not be appended to the same results store without removing the superseded error entries: the leaderboard counts every entry, so mixed attempts inflate `runs` and `api_fail`.
3. **ChartVerse Q4_K_M — tested, failed the smoke (2026-10-12):** artifacts (Q4_K_M + mmproj-Q8_0, checksums verified) at `/workspace/data/models/chartverse-2b-gguf`; llama.cpp `f2cc728` CUDA build persisted at `/workspace/data/tools/llamacpp-f2cc728-cuda128-bin.tar.gz`. Served on port **8085** (8081 is owned by the container's nginx; registry `base_url` updated accordingly), `--alias` matching `api_model`, `-ngl 99 -c 24576`. Three configurations tried (greedy; `temperature 0.6/top_p 0.95`; plus `--image-min-tokens 1024`) — all hit `finish_reason=length` at 8,192 tokens with unbounded, partially hallucinated analysis and no JSON. Not a repetition loop and not a thinking budget: the 2B model does not converge on this task shape. Any retry requires a protocol change (concise-answer instruction in a separate root), which was deliberately not made during the first pass. VRAM was released after the server was stopped.
4. **VFAi-X last, conditional on disk:** pin the *vision-capable* revision of `tjarvis91/vfai-x-3.5-9b-options`; it is a legacy research checkpoint, and the shim has no `--revision`, so pass a pinned local snapshot or add revision support before measuring it. Start with `--load-4bit` on port 8083, BF16 compute, a bounded image size, and one no-shot chart. Verify that bitsandbytes really quantized the model **and** image understanding still works; a successful load alone is not sufficient. Four-bit saves VRAM, **not** download space: the on-the-fly loader still needs the original approximately 18 GB BF16 source. With only ~22 GiB local free, stage **one copy only**, leave several GiB of free scratch, and do not start if the downloader duplicates weights or capacity is insufficient. Seek more local POSIX scratch or a verified quantization of this exact vision fine-tune if necessary; do not substitute a quantized base Qwen model. BF16 on the 24 GB GPU is a secondary one-chart load test only if headroom allows. Native Linux vLLM FP8 is a later fallback only after confirming this exact revision and its multimodal path are supported. Do not silently fall back to CPU for a full benchmark.

If CUDA `llama-server` is ready before the Amsi download, running ChartVerse Q4 first is also reasonable; both low-risk models come before VFAi. At every handoff, stop the previous process and confirm `nvidia-smi` returns to baseline. Model files can remain on disk only if scratch allows, but never keep two models resident on the GPU.

## Single-model run protocol

Run commands from `/workspace/trading_framework` with `/root/.venvs/trading/bin/python`. Set `HF_HOME` to a local path for the HF services. Start **only** the selected model's service on its registry port, wait for `/v1/models` (and `/health` for the HF shim), and watch the server logs and `nvidia-smi`. If llama.cpp or vLLM validates the request's `model` field, make its served alias match the registry's `api_model`. Start HF runs with `--max-pixels 802816 --max-new-cap 2048`; verify the processor's actual input-token count, and increase the cap only for truncation with available VRAM. The llama.cpp server should have enough context for input plus output.

First check the pipeline without contaminating the three-model results:

    /root/.venvs/trading/bin/python vlm_benchmark.py run \
      --mock oracle --root /root/vlm_work/runs/mock \
      --split val --items 13_PTON_2024-08-26 --workers 1

For the real run, set `MODEL_KEY` to **one** of `amsi-fin-o1-hf`, `chartverse-2b-hf`, or `vfai-x-9b-hf`. Use the *same* prompt and output cap for a one-chart smoke run and the subsequent full validation run, so a successful smoke response is cached. Example for Amsi:

    MODEL_KEY=amsi-fin-o1-hf
    /root/.venvs/trading/bin/python vlm_benchmark.py run \
      --models "$MODEL_KEY" \
      --root /root/vlm_work/runs/baseline \
      --split val --items 13_PTON_2024-08-26 \
      --workers 1 --repeats 1 --max-tokens 2048

Inspect `status`, `parse_failed`, `finish_reason`, raw answer, image grounding, latency, and GPU peak before continuing. A blank/length-truncated reply is a failed smoke test, not a usable score. Then run the remaining validation charts with the same key/root/settings; the successful smoke chart will be skipped by cache. For better crash resilience, use individual `--items <chart-id>` invocations with a result snapshot after each rather than waiting for all 8. Do not use a comma-separated model list or `--first-pass`.

After all three validation runs, compare results and freeze each model's configuration. Only then make a second sequential pass over models for held-out test, restaging one model at a time and restoring the baseline results before each pass. Set `MODEL_KEY` to the one active model before each invocation:

    MODEL_KEY=amsi-fin-o1-hf
    /root/.venvs/trading/bin/python vlm_benchmark.py run \
      --models "$MODEL_KEY" \
      --root /root/vlm_work/runs/baseline \
      --split test --workers 1 --repeats 1 --max-tokens 2048

Persist completed test batches before changing model or container. After all three models have finished, restore the complete baseline results to local disk and run:

    /root/.venvs/trading/bin/python vlm_benchmark.py report \
      --root /root/vlm_work/runs/baseline --split val,test

Do the no-shot single-image baseline first. `--shots train,val` adds 19 example images plus the query image and may exceed VFAi's 32K context/VRAM; treat few-shot runs as a separately named protocol and result root after baseline, never as an unannounced change to it.

## Stop conditions and completion

- Stop on storage permission/readback failure, insufficient verified local disk headroom, an unpinned or text-only checkpoint, unsupported 4-bit vision path, GPU OOM, empty/truncated response, or invalid resistance-level output. Investigate rather than reporting a substituted model as a success.
- Each of the three model identities has a verified one-image response and its own completed validation run with one model/one worker. If VFAi is blocked, record the exact blocker and required storage/runtime alternative; do not call a two-model run a three-model result or proceed with a partial comparison without user agreement.
- Freeze settings before test; complete each held-out test model separately, persist raw/results outside the ephemeral overlay, and produce a report from the restored snapshots. Do not push or commit model artifacts into the Git repo.
